## 0.1.0-beta.1

First beta candidate; not yet published. The application and Windows WebKit engine have independent versions and release gates.

- Align the initial Windows WebKit candidate with application version `0.1.0-beta.1`. Resume interrupted source-cache initialization without discarding downloaded Git objects or partial files; preserve unrelated cache states and test recovery on Windows PowerShell.

- Complete the Windows-to-macOS integration review, record scoped native results and first-publication prerequisites, and synchronize the candidate version. Fix asynchronous macOS Inspector docking so it cannot shrink the measured viewport, and route Inspector shortcuts through the focused native browser. Run the AppKit assertions in CI; retain explicit platform gaps in the handoff.
- Give the macOS tools WKWebView an arranged native host so the offline Chrome DevTools frontend paints its composited widgets; verify DOM/styles and Console evaluation in the presented window.
- Keep exact logical viewport dimensions at fractional macOS Fit scales instead of forwarding floating-point bounds drift to WebKit; add a regression for the observed one-pixel loss.
- Allow managed Windows cross-compilation without a locally built C++ compositor, while retaining native Windows bundling. Accept compatible mise-managed Python patch versions in an existing uv environment.

### Viewport workbench

- Start on an offline welcome page when no website is configured, with Home navigation and metadata-owned repository/documentation links. Move the color demo and receiver-dependent calibration action into Developer tools. Show the current document title in the active illustrative tab, with native width-based tail ellipsis and full Windows accessibility text.
- Extend native fixed-container and dialog-backdrop colors into obscured insets without changing the real viewport or scroll geometry. Windows queries WebCore through a versioned asynchronous four-edge API; macOS enables the system extension when available and reports its native acceptance separately.
- Avalonia desktop viewport workbench, with system WKWebView on macOS and the pinned source-built Windows WebKit backend. It provides Safari and immersive containers, independent screen and exterior geometry, eight body/fold mappings, and 24 initial/scrolled Safari states, including Open single- and multiple-tab variants. The Open multiple-tab shell uses two illustrative tabs that share derived presentation frames; original captures and viewport reservations stay intact. Selected-tab bounds and centered titles follow the measured containers. Unknown hardware dimensions remain null.
- Body/canvas coordinates stay separate from screen/body coordinates. Closed 180° presents an inverted portrait body and keeps the measured landscape layout. Windows uses live native rotation, transformed screen masks and inverse pointer mapping; macOS uses NSView coordinate transforms.
- SukiUI host on Avalonia 12: a real address bar bound to native navigation, grouped settings, a status bar, light and dark themes, shortcuts, accessibility labels and persisted host settings. The persisted set excludes body angle. Calibration labels attach only to the local receiver page and keep query strings and fragments. Presentation changes keep the loaded document, an intentional mode switch still recreates the view, and fixture translation keeps the scroll position. Deferred address text stays distinct from user edits, so native navigation and localized fixture labels keep updating the address bar.
- Persisted English and Simplified Chinese UI, with live native and fixture updates and resource/scene-invariance tests.
- Both containers set the observed iPhone Safari User-Agent through native WebKit before the first request, so the HTTP identity matches the page-visible identity. The frozen OS token, the measured desktop engine and platform values, and the separate developer-tools frontend identity each stay in place.
- On macOS, the native document-end canvas fill is restored, a passive solid fixed footer extends its color, and the native preview is placed after layout.

### Windows WebKit

- Replace repeated receiver-side process-handle acquisition with an inherited parent capability and UI-pushed, connection-owned Web/GPU/Network capabilities acknowledged before initialization. Retain capabilities through thread-safe references without cloning process handles on lookup. Preserve ordinary handle-transfer ownership, constrain inheritance, reject stale handshakes and add cold HTTP/inline navigation, real source-pixel timing, Network crash recovery and native lifetime checks.
- Complete GPU initialization before isolated Canvas readback waits, build Network connection parameters from the current configuration after bootstrap, and preserve the current renderer observation while queued document messages are being verified.
- Windows uses the Avalonia Windows WebKit backend: non-testing host API v2, a locked portable source build, explicit vcpkg interpreter ownership, runtime integrity checks, and native acceptance evidence checked against compiler source checksums. Startup discovers the validated source-built runtime. The backend keeps four-side continuation and the viewport, fixed and scroll geometry, with independent logical scene and backing scales. The host window is opaque for native child-window composition, and live content shows through native chrome alpha. Each final measured frame is committed once. Document-end scroll clamping leaves compact chrome collapsed. A passive native color surface fills only beyond the actual document end; a solid full-width footer is a separate approximation.
- Windows GDI shell controls are replaced by DirectComposition blur of the live WebKit surface and Direct2D/DirectWrite chrome. Rounded transparency, material and glyph opacity stay independent. The shell includes layered glass, passive camera/Wi-Fi/clock illustrations, independent Safari shell actions and DirectWrite compact-label measurement. Versioned native RGB edge sampling uses theme priority, debounce and stale-generation rejection, and those samples drive chrome color. Desktop scrollbar gutters are removed. The hosted window and the Avalonia holder both clip to the screen path. Non-composited content under obscured insets paints while the layout geometry stays unchanged.
- Fractional Fit follows native hard-clip pixel rounding, and software paint is flattened onto the explicit page background before GDI upload. When a backing-store translation is not an integer device-pixel move, the view paints native scroll damage. Physical window bounds update independently of the logical viewport. Resize skips copying stale pixels, and a size or ancestor-clip change invalidates the live surface. An obscured-inset change, including the strip exposed by compact chrome, requests a full scene repaint.
- Accelerated frames go through WebKit's native offscreen backing store with the submitted logical size and scale. Rendering counters are recorded, and unchanged host text measurements are cached. WTF timer deadlines run while Avalonia owns the Windows message pump. The timer repair and the subsequent initial-navigation IPC repair address separate causes. Source-frame timing and final desktop FPS are separate measurements, and final desktop composition still needs its own visual check.
- Windows website storage persists across launches. Rotation keeps the document, form state and history. Navigation timing is exposed, and early page paints stay visible while DOM observations are pending. The native host starts from an application manifest, with corrected DPI, preview zoom and shell font scaling.
- Windows has a native 24-state viewport baseline at 200% DPI. Ordinary-page regression covers 152 pairs, including painting v2, unmodified static-boundary checks, and physical-display checks at 100%, 150% and 200% DPI. Those checks preserve the document, viewport, fixed and sticky elements, and scroll position. Broader native input, DPI and appearance acceptance remains pending.
