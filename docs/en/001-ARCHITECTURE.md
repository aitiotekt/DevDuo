# Architecture and browser containers

Avalonia owns the host window and shared device/scene selection. `NativeWebView` hosts a system WKWebView on macOS or the pinned Windows WebKit Port on Windows. Platform renderers compose browser content and Safari illustrations inside an independent screen mask; exterior artwork can be toggled without removing that mask.

## Code map

| Layer | Source | Responsibility |
| --- | --- | --- |
| Host | `src/DevDuo/Host/`, `src/DevDuo/App.axaml`, `src/DevDuo/Styles/` | Main window, address/settings/status controls, localization, preferences and preview sizing |
| Browser | `src/DevDuo/Browser/` | Native view lifetime, shared navigation/title state, built-in page selection, calibration labels and scroll/chrome policies |
| Developer tools | `src/DevDuo/DeveloperTools/` | Native Inspector coordination, CDP transport, proxy contracts and the separate system WebView tool window |
| Scene model | `config/`, `src/DevDuo/Device/` | Paths, separate body/canvas and content/body transforms, measured scene mapping, widget/tab frames and presentation options |
| macOS | `src/DevDuo/macos/WebViewBridge.swift`, `src/DevDuo/macos/DeveloperWebViewBridge.swift` | System WKWebView, native glass/clipping/insets/color sampling and the separate developer tool WebView |
| Windows | `src/DevDuo/windows/` | WebKit C host bindings, physical screen/input transforms, clipping, logical scene/backing scale and the native DirectComposition compositor |
| WebKit runtime | `native/webkit/windows/` | Pinned engine lock, production host patches, source build and runtime archive support |
| Application web assets | `src/DevDuo/WebAssets/Pages/`, `src/DevDuo/WebAssets/Scripts/` | Offline welcome/color pages, passive browser observer and page debugging bootstrap; copied with the application |
| Calibration | `web/`, `scripts/python/`, `scripts/swift/`, `scripts/DeviceHubUITests/` | Browser records, actual Safari frames, captures and comparisons |

The receiver serves fixed calibration assets and writes local JSON; it does not control the app or execute page-supplied commands. Command ownership and setup are in [Contributing](../../CONTRIBUTING.md).

Portable tests are separated by responsibility: `tests/DevDuo.Core.Tests` covers shared state and measured invariants, `DevDuo.Localization.Tests` covers catalogs and language behavior, and `DevDuo.Debugging.Tests` exercises real loopback CDP transport. `DevDuo.Windows.Tests` owns native app acceptance, with scenarios in `Checks/`, lifecycle/server helpers in `Harness/` and evidence collection in `Evidence/`; `DevDuo.WebKitProbe` owns standalone engine diagnostics. Compilation and portable tests do not establish native acceptance. See [Platform parity and macOS acceptance](015-PLATFORM-PARITY.md).

## Modes and interaction

- **Safari approximation** adds page-colored floating controls and changes the content viewport with actual scrolling. Open offers single/multiple-tab variants; the switch illustrates shell geometry rather than managing real tabs.
- **Immersive App WebView** removes browser chrome and uses the full logical scene. Changing the outer outline does not remove native screen clipping.

A fresh profile starts with Safari, Closed, body 0°, 1:1; saved host settings restore other choices, but every launch starts at body 0°. The eight measured mappings determine the actual scene, including the rotation-history qualification at Closed 180°. Fit follows the available preview area and never exceeds 1:1. macOS Fit scales the native coordinate space while preserving CSS dimensions; Windows Fit changes native backing scale with page zoom fixed at 1 and preserves the logical WebKit viewport. Use the [scene matrix](005-SAFARI-SCENES.md) for viewport sizes, tab reservations and selected-tab geometry. A partial-fold perspective model is unavailable.

Back/Reload use native navigation; other illustrated widgets have limited demo interactions. Both containers use the recorded mobile Safari request identity; the actual engine, platform, DPR, orientation, safe areas and keyboard remain native. A Safari-looking container does not make the engine iPhone Safari.

Body angle rotates the exterior in the preview canvas; content relative to the body is a separate transform. The measured scene retains its original logical dimensions, Safari frames and viewport reservations. `NativeWebView` receives physical screen extents, crop offsets and the final scene-to-canvas quarter turn. Windows rotates the complete live page/material/glyph tree through presentation API v1 alongside composition API v3. Rotated scenes keep a full-size cloaked WebKit child in an owned `WS_EX_NOREDIRECTIONBITMAP` source host, preventing the smaller physical screen's HWND ancestors from clipping rasterization before rotation. The source host contributes no desktop pixels and is released with the compositor. Pointer coordinates and accessibility rectangles use inverse/forward transforms; Avalonia logical focus delegates to the real WebKit HWND. macOS rotates the native NSView frame, allowing AppKit to convert input coordinates. See the [two-coordinate-system contract](005-SAFARI-SCENES.md#body-and-content-coordinate-systems).

## Host controls and navigation

SukiUI 7 on Avalonia 12 supplies the host control theme. `Styles/DevDuoStyles.axaml` adds light/dark tokens, spacing, typography, icons and component classes. These styles apply only to Avalonia host controls; the device outline, screen mask, Safari widgets, tab text and viewport reservations remain with the platform renderers and measured configuration. Host surfaces are opaque and occupy separate grid cells. SukiUI toasts, dialogs and other in-window overlays are not used, because Avalonia content cannot draw above a native browser child. Avalonia moves native children but does not clip them to scrolling ancestors, so the native view is not inside the preview scroll viewer: a transparent slot scrolls with the outline, and the native view sits in a layer above it, sized to the slot's visible part (scroll bars stay uncovered). A native clip view (`devduo_set_viewport` on macOS, a parent window on Windows) offsets the full-size container inside it, so the container frame, scene scale, CSS viewport and telemetry do not change while scrolled.

The host address bar is bound to the active native view. macOS observes WKWebView `url`, `title`, `isLoading`, `estimatedProgress`, history flags and navigation failures, then calls back through `devduo_set_navigation_callback`. Windows uses ordinary WebKit C navigation callbacks and polls URL/title/progress/history metadata on the UI thread. Callbacks are posted to the UI thread and ignored once their native container is destroyed; cancelled or superseded loads are not failures. Addresses must be http/https. A missing scheme becomes `http://` for loopback, `.local` and private-network hosts and `https://` otherwise; other schemes are rejected. Query strings and fragments are kept. Measurement labels (`device`, `pose`, `browser`, `state`, `displayMode`, `notes`) are added only to the local receiver page (loopback, port 8765, path `/`), replace earlier labels and are hidden in the address bar.

| Change | Native view |
| --- | --- |
| Language, theme, multi-tab strip, material tuning, outline | Reconfigured or moved in place; page, history and scroll are kept |
| Preview scale | Resized in place; calibration labels update through history state without reloading |
| Body angle | Updates masks, logical geometry and live presentation in the same native view; document, form/JavaScript state and history survive; scroll can clamp to the new viewport's valid range |
| Fold, container mode | Recreated at the current website, welcome page or color laboratory; scroll and history restart and the status bar says so |

Shortcuts: ⌘L/Ctrl+L focuses the address, ⌘R/Ctrl+R or F5 reloads, Esc stops loading, ⌘[ ⌘] or Alt+←/→ move through history, ⌘S/Ctrl+S saves state and ⌘\\/Ctrl+\\ toggles settings. macOS also lists them in a native **Navigate** menu so they work while WKWebView has focus. Windows forwards native WKView keyboard messages and the panel's command-key chain; IME and full keyboard traversal still need acceptance. Host controls carry localized automation names, tooltips with shortcuts and help text for disabled options; the status message is a polite live region.

`Host/PreferenceStore.cs` keeps host settings in the optional `host` object of `DevDuo/preferences.json`: `theme`, `containerMode`, `fold`, `previewScale`, `deviceOutline`, `showTabStrip`, the four material values (null keeps `config/safari-shell.json`), panel expansion and `lastUrl` (http/https only). Fields are validated separately; an invalid field uses its default and is reported. Body angle is never stored, so Closed 180° is reached only through the recorded clockwise sequence. A valid `DEVDUO_URL` overrides a remembered website; without either, the app loads its built-in offline welcome page without a preceding network navigation. Home and the color laboratory are distinct built-in pages and do not replace the remembered website. Their links come from the project metadata. Calibration remains an explicit Developer tools action requiring the receiver service. **Reset settings** restores the defaults and body 0° without changing language or the current page. File format and language behavior are in [Localization](011-LOCALIZATION.md).

The active illustrative tab displays the current verified document title, including dynamic title changes. An empty or not-yet-confirmed title uses the localized generic page label. The inactive slot stays illustrative. Native text layout applies tail ellipsis at the existing text width; the model and Windows accessibility names retain the full title, and no tab container, close-control or font geometry changes.

## Developer tools and page proxy

Developer tools is the first expander in the settings sidebar and starts collapsed on every launch. It contains native Inspector, native remote inspection, CDP/chii and proxy controls, followed by the color demo, calibration action and calibration-service hint at the end. Expansion belongs to the current window session and survives language changes and settings reapplication; it is neither restored nor saved. Legacy `developerExpanded` JSON is accepted as an ignored unknown field. Sidebar visibility, material and diagnostics expansion continue to persist. Native local inspection opens a detached window so docking cannot change the measured viewport. Local and native remote Inspector connections are mutually exclusive; page CDP is independent. Both remote services start disabled on every launch. Listener/LAN preferences, proxy settings and an explicitly configured CDP bearer token persist; enabled flags and temporary frontend capabilities do not.

| Path | Transport and scope |
| --- | --- |
| Native local Inspector | A separate platform WebKit Inspector window; engine capabilities depend on the build. |
| Windows native remote | `hostDeveloperApiVersion: 1` starts/stops WebKit's inspector TCP server. The `webkit-inspector-socket` address requires a compatible WebKit client, not a Chrome CDP/WebSocket client. Native TCP has no DevDuo token authentication. |
| macOS native remote | Public `WKWebView.isInspectable` enables Safari Develop discovery. This path creates no custom port or LAN listener. |
| Page CDP | `DeveloperTools/CdpDebuggingService.cs` hosts HTTP/frontend/discovery and a single page WebSocket. `WebAssets/Scripts/remote-debugging.js` wraps chobitsu 1.8.6; `scripts/package-debugging.mts` packages chii 1.15.5. Installed apps need no Node process or CDN. |

CDP binds loopback unless LAN access is explicitly selected, which opens active IPv4 interfaces. Its base address and routes are fixed. Loopback permits an empty optional bearer token; LAN CDP requires one. With a configured credential, discovery and page sockets require an Authorization bearer header. Public frontend assets contain no target data, and the built-in frontend receives a separate per-start, same-origin socket capability rather than the persistent credential. Relative to the displayed base URL, `json/list` and `json/version` expose qualified discovery, `devtools/page/devduo` accepts raw CDP WebSocket messages, and `front_end/chii_app.html` serves the real chii frontend. Unknown Host headers and cross-origin browser WebSockets are rejected. A second debugger is rejected rather than sharing IDs. The advertised protocol version is a transport convention, not complete CDP support.

The complete offline script is installed at native document start and evaluated immediately in the current page. Responses/events use a dedicated native script-message handler; commands use native evaluation into the bridge. The target opens no debugging WebSocket and loads no remote debugging script, avoiding dependence on HTTPS mixed-content or `connect-src` permission. Individual operations can still face CSP, cross-origin resource and upstream implementation limits. This is page-world instrumentation, not a browser security boundary.

chobitsu offers DOM/CSS, Console/Runtime, storage and observed network operations where supported. It cannot provide native JavaScript breakpoints, CPU/heap profiling, complete navigation/resource traffic, browser-wide targets or engine protocol equivalence; some upstream compatibility commands are no-ops. Mid-document enablement cannot recover earlier Console/Network observations. A new document resets the transport and refreshes only an existing chii tool window to reconnect; external clients reconnect themselves. Duplicate readiness from one document does not refresh the tool. Stop closes sockets/listeners, rejects stale callbacks and removes the dedicated future script without removing the passive measurement observer. It mutes the current bridge; installed JavaScript hooks require an explicit user page refresh to disappear.

Proxy changes preserve the document, viewport and scroll and configure the native website data store for later requests. Windows supports system, direct and custom modes. macOS uses public `WKWebsiteDataStore.proxyConfigurations` for system/custom; an empty list restores system behavior and cannot force direct access, so direct mode reports unsupported. Custom `http`, `https` or `socks5` endpoints have a port and no credentials, query or fragment; authentication/PAC are outside this UI. Existing connections may survive under native networking rules. macOS Inspector, injection and proxy changes still require native acceptance on macOS.

## Drawing below floating chrome

On the validated macOS 27 runtime, Closed mode keeps a full-size WKWebView and sets public `obscuredContentInsets`. A 466 × 678 native frame with side 84 / bottom 98 insets has a 382 × 580 page viewport; compact bottom 80 yields 382 × 598. Normal document flow continues below the address bar, while fixed-bottom elements stay within the smaller viewport. The 270° scene moves the side inset to the left.

`minimumViewportInset` / `maximumViewportInset` describe the bottom 80…98 range: the independent probe measured 100svh = 580, 100lvh = 598, and 100dvh = 580/598. Immersive mode clears these insets. Fit scales presentation without changing those CSS dimensions; state records distinguish actual viewport, drawing frame, DIP and obscured insets.

macOS Open still reserves a smaller native frame and its top-chrome continuation is a derived-color approximation. The [Windows WebKit backend](014-WINDOWS-WEBKIT.md) uses full native drawing frames with genuine four-side obscured insets and independent logical view/backing scale; page zoom stays at 1 during Fit. On the tested WK runtime, `takeSnapshot` omits continuation visible in the actual window. Inspect the presented window as well as snapshots. The archived [inset probe](../../scripts/archive/README.md) and original local `captures/desktop-validation/under-chrome/` records document that distinction.

API references: [WKWebView obscuredContentInsets](https://developer.apple.com/documentation/webkit/wkwebview/obscuredcontentinsets), [WebKit viewport support](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/).

WKWebView retains native canvas/under-page background drawing. Where supported, the macOS bridge enables the system content-inset background-fill implementation and removes its own opaque footer/side surfaces from that path. This uses the engine's fixed-container and backdrop color extension, without changing DOM styles, viewport reservations, fixed frames or scroll range. The changed macOS path still needs native acceptance. If the private capability is absent, diagnostics expose that limitation and retain the legacy read-only DOM approximation for opaque full-width fixed footers; that fallback does not certify translucent masks. Windows uses the explicit [native four-edge color API](014-WINDOWS-WEBKIT.md#translucent-fixed-overlays). The [calibration guide](003-CALIBRATION-WORKFLOW.md#translucent-modal-backgrounds) separates the requested Safari behavior from desktop acceptance.

Native placement is synchronized at Avalonia's `Loaded` dispatcher priority after layout, including the clip/content configuration. The AppKit containers disable implicit subview resizing and relayout when their frame size changes. This keeps screen content aligned with exterior artwork at startup, resize and Fit; `nativeClipGeometry` records the full container, logical bounds and clip offset. See [acceptance](003-CALIBRATION-WORKFLOW.md).

## Material and diagnostics

macOS composes WKWebView and sibling AppKit surfaces beneath one Bezier mask, avoiding ordinary Avalonia overlays above native browser children. The current macOS 27 package uses `NSGlassEffectView` clear/tint. Its older `NSVisualEffectView` branch requires a lower-target rebuild and separate runtime validation. Tint, material contribution, shadow and radius are tunable; the private iOS Liquid Glass blur/refraction kernel is unknown.

Shell appearance independently controls Light/Dark glyph/material treatment and native page color scheme. Both platforms sample a rendered WebKit edge strip even with opposing theme-color hints, retaining meta as diagnostics and computed background as a labeled fallback. Windows content color API v1 returns only RGB/status from ordinary snapshot IPC; its images never enter page rendering. Sampling is debounced, asynchronous and can lag moving content; navigation/document/geometry generations reject stale results. The D3D11/DirectComposition bridge consumes the live WebKit HWND redirection surface, applies Gaussian blur and color correction before rounded clipping, and draws tint, directional highlights, borders, shadows and clear glyphs separately with Direct2D/DirectWrite. Passive camera/Wi-Fi/clock illustrations and independent shell actions follow macOS scene rules. Document boundary strips use the root-background rule independently of toolbar tint; valid horizontal flow remains visible. Broader input, DPI and presentation acceptance remain separate gates; see the [Windows implementation and limits](014-WINDOWS-WEBKIT.md#live-surface-composition).

**Color demo** is a separate fixture for theme hints and live content sampling. **Save state** and `window.devduoContainerTelemetry` expose requested/actual frames, scroll/chrome state, visible versus hit bounds, tint source/RGB and material parameters. `previewScale` records the actual presentation scale. Checkout state files go to `captures/desktop-validation/container-modes/`; installed apps use local application data under `DevDuo/captures`. `DEVDUO_OUTPUT_DIR` overrides that location.

For measurement semantics and provenance, use the [measurement contract](002-MEASUREMENT-CONTRACT.md). For acceptance and recorded platform limits, use [calibration and validation](003-CALIBRATION-WORKFLOW.md). Future host controls remain separate from measured Safari geometry; see the [roadmap](100-ROADMAP.md).

The host-window-owned `ControlApiService` uses Kestrel for an independent, opt-in loopback REST listener. Validated commands run on Avalonia’s UI dispatcher against the same navigation/settings operations; they do not own native handles or outlive a closed window. Device/container rebuilds leave the listener intact. The offline Swagger UI and OpenAPI JSON contract are described in the [usage guide](004-USAGE.md#rest-control-api).
