# Windows WebKit continuation backend

The standalone C++/Win32 investigation uses an official Windows WebKit build. The Avalonia application exclusively uses the Windows WebKit Port, built from the same pinned source with a maintained non-testing host API. No browser backend selector or alternative engine is present. The [Windows handoff](009-WINDOWS-HANDOFF.md#document-end-continuation-research-2026-10-22) owns the Safari comparison and implementation target.

## Real continuation and native boundary correction

The sibling-window correction in this section belongs to the standalone diagnostic. The application uses GPU boundary strips with the same document rule, plus the engine painting patch and live-surface compositor described below.

At the tested 192 DPI, `WKViewCreate` retains a 764 × 1356 physical-pixel child: 382 × 678 DIP. A real bottom inset of 98 gives inner/client/visual dimensions 382 × 580 and fixed bottom 580; inset 80 gives 382 × 598 and fixed bottom 598. The initial inset is applied before navigation. Numbered flow and an independently animated counter genuinely paint below the smaller viewport. No screenshot is rendered, no DOM dimension accessor is replaced, and actual UA/DPR/screen reporting remains native.

The uncorrected port retains old rows after the document end enters that area. For the 2400-pixel page this starts after scrollY 1722 and is obvious at maximum Y 1820. Native force repaint, background-extension and preference experiments did not eliminate it. Direct post-paint GDI drawing also did not establish a reliable presented correction. These are retained failed experiments, not a confirmed engine root cause.

`ContinuationSurface.h` now adds a passive native **solid-color sibling** above the opaque browser and below the address bar. Read-only messages from the shared browser observer provide actual document height D, scroll Y and viewport V. For bottom inset B, valid live flow length is `L = clamp(D - Y - V, 0, B)`. The surface covers only `[V+L, V+B)`; WebKit continues drawing `[V,V+L)`. At Y 1770, 50 pixels of real flow remain; only the remaining 48 are filled. At Y 1820, all 98 are background. CSS coordinates are converted through actual native client dimensions and viewport/inset size, rather than assuming a DPI. The surface is nonactivating and returns transparent hit testing.

The C interface used here does not expose a verified resolved under-page color getter. The fill therefore reports its explicit **opaque html/body CSS fallback, otherwise white**, independently of toolbar theme tint. An opaque, solid, visible full-width fixed footer uses the shared observer's eligibility check and may color the whole inset; narrow/removed footers clear this separate approximation. Gradients, alpha backgrounds and Safari's color-history heuristics are not generalized. Neither correction changes viewport reservations, fixed frames, document size or scroll range. Fixture row-count changes are deliberate test inputs, never an implementation workaround.

The matrix records both insets, near/end positions, full/narrow/removed footers, short documents, growth/shrink and scroll-away/return. Native observations distinguish valid-flow length, fill coordinates/color, visibility, window frames and paint count. Actual-window wheel and live-animation observations supplement those records. The sibling corrects the final host scene; it does **not** repair WebKit's retained backing pixels internally.

## Host API source build

The [manual runtime release workflow](013-RELEASE.md#windows-webkit-runtime-releases) reuses a persistent self-hosted build tree. Application releases consume its metadata-pinned archive without rebuilding WebKit; local source builds remain available. Release-tool checks are separate from native acceptance.

The official prebuilt DLL exports only the testing inset setter. The maintained `patches/0001-windows-host-viewport-api.patch` adds a versioned Windows host C API: `WKViewSetObscuredContentInsets` validates finite/nonnegative insets against the logical native view, then calls `WebPageProxy::setObscuredContentInsets`. This updates the proxy's persistent configuration and uses ordinary `WebPage::SetObscuredContentInsets` IPC. `WKViewSetUnobscuredSizeRange` forwards the real default/minimum/maximum unobscured sizes for engine viewport units. The patch neither enables testing IPC nor modifies JavaScript geometry. It is a DevDuo port extension, not an API already supplied by upstream artifacts.

Host API **v2** also adds `WKViewSetHostPresentationGeometry`: a genuine logical scene size and physical backing scale, shared by native drawing and mouse/wheel coordinate conversion. This separates presentation from layout without changing DOM styles/getters. The earlier page-zoom experiment failed: 50% doubled small/large viewport units, while 75% exposed the port's integer-DIP rounding and produced a 381.33-pixel visual width. Those failed records remain intact. The v2 route keeps page zoom at 1, supplies the actual engine view size, and preserves 382 × 580/598 plus fixed frames and scroll ranges at fractional Fit. DPR reports the real selected backing scale.

The presentation patch also conservatively encloses physical damage rectangles, rounds backing dimensions up and aligns native raster origins to device pixels. Truncating logical rectangles after fractional scaling could leave the last row/column unchanged after a document shrank. These changes are Windows-only and alter raster allocation/clipping, not layout or document dimensions.

`patches/0002-windows-content-painting.patch` adds **content painting v1**. Non-composited `ScrollView::paint` and `repaintContentRectangle` previously clipped to the unobscured layout viewport, producing black below the unmodified static color page. The Windows-only painter expands its canvas clip through obscured insets and includes top/left insets in its paint origin. Canvas painting must reach beyond a shortened document's exact boundary to update fractional edge pixels; the host independently clips valid document flow and fills only beyond it. Layout, hit testing, fixed/sticky positions, viewport units and scroll limits are unchanged. No fixed marker, page-style change, animation or repeated forced repaint is required. The runtime manifest records all maintained patch hashes and current frozen build inputs. Startup requires viewport API v2, painting v2 and content color API v1, and verifies runtime-file hashes; older runtimes must be rebuilt.

The same patch corrects the retained scroll-copy domain. A partial horizontal scroll exposed black in the left inset even after ordinary painting was fixed: `windowClipRect` and the copy rectangle still excluded obscured content. Copying now covers the full native drawing domain. Software overlay scrollbar rectangles and their copied positions are invalidated explicitly so their excluded strip cannot retain black or moved scrollbar tracks. This is engine damage handling on an actual scroll, not a repaint timer or a forced-repaint loop. The left-84/scrollX-40 regression preserves 40 CSS pixels of real flow and 44 of root background.

The native-build `mise.windows-webkit.toml` environment and lock select portable CMake, Ninja, Ruby, Strawberry Perl, gperf, pkgconf and vcpkg. The normal mise Python line remains authoritative. Custom vcpkg host/target triplets explicitly pass those interpreters/generators, preventing a separate embedded Python from taking over. Visual Studio C++/Clang and Windows SDK remain detected system dependencies. vcpkg owns the upstream-pinned library manifests/registries and internal dependency build helpers. The GnuWin32 gperf distribution has a fixed verified archive because no newer portable Windows release is available.

## Live surface composition

Compositor presentation API v1 adds a final quarter-turn/translation of the complete tree, independently of measured scene layout. For rotated scenes, the original WebKit HWND is a [cloaked layered child](https://learn.microsoft.com/en-us/windows/win32/directcomp/how-to--animate-the-bitmap-of-a-layered-child-window) in a full-size owned source host with no redirection bitmap; the physical screen receives the rotated live tree. Keeping the source inside the smaller physical clip loses ordinary paint pixels before composition. `WindowsScreenPresenter` inversely maps pointer coordinates and forwards focus to the real source HWND; screen masks and shell accessibility rectangles follow the presentation transform. This app-DLL capability needs an app rebuild, without changing the WebKit runtime hash or viewport API. The [scene contract](005-SAFARI-SCENES.md#body-and-content-coordinate-systems) defines body-zero conventions; the [handoff](009-WINDOWS-HANDOFF.md#native-acceptance-checklist) records acceptance and remaining fractional-Fit/DPI limits.

`windows/HostCompositor.cpp` exposes composition API v3 to `WindowsComposition.cs`. It creates a BGRA D3D11 device, a Direct2D device and a DirectComposition target above the WebKit child. `IDCompositionDesktopDevice::CreateSurfaceFromHwnd` imports the child's **live DWM redirection surface**. This route avoids adding a separate ANGLE shared-texture export to WebKit. The host enables WebKit's existing offscreen-rendering mode before first navigation so software and accelerated page frames reach the same retained backing store and layered window. The accelerated WC path includes GPU pixel readback into WebKit's shared bitmap transport; this is a performance cost, not a zero-copy presentation claim. No screenshot API, stitched image or DOM-size override supplies the page. WebKit remains the sole page renderer and input owner. The browser's layered-window alpha is 255 to expose its source surface; material strength never reduces foreground glyph opacity.

The painting patch normalizes accelerated frame metadata to the submitted logical view size and backing scale, matching the nonaccelerated path. The bitmap retains its physical-pixel dimensions. The existing backing-store state guard rejects stale resize callbacks, preventing an old frame from being interpreted at a newer scale. Physical HWND synchronization and event-driven full damage handle resize and ancestor-clip changes without navigating the page. Host observation updates publish one telemetry payload per layout and reuse an exact text/size measurement until its language or native resources change. Rendering and observer counters diagnose this pipeline; they are not final desktop FPS measurements.

Changing obscured insets can move the paint origin while retaining the outer view size. On Windows WC, an actual inset change requests one full drawing-area update and clears queued scroll-copy damage. Invalidating only the HWND would redraw the old backing store. The isolated `just test-windows-presentation-insets` check covers the newly exposed strip of the unmodified color fixture; source-raster results remain distinct from final DWM visual acceptance.

Avalonia dispatches Windows messages without running WTF's own `run/cycle` loop. The Windows RunLoop patch therefore arms one native timer on its existing message-only window for the nearest monotonic deadline. Due work still passes through WTF's existing `FireTimerMessage` queue and cancellation checks. Identical deadlines are not repeatedly postponed; cancellation, repeating callbacks and window destruction rearm or release the timer. The same queue remains usable by WTF's own loop. This services native timers rather than polling, forcing paints or draining Avalonia's messages inside a nested loop.

Composition order is live page/valid continuation, document-boundary strips, local Gaussian blur, rounded tint/border/shadow, then clear text/icons. Each blur samples the same page/boundary source before shell decorations, preventing recursive self-sampling. Blur precedes the rounded clip and clamps source edges. Surfaces use premultiplied alpha; Direct2D/DirectWrite draw foreground glyphs separately. Hit and optical frames remain distinct. Full selected-tab containers, exposed text clips, localized names and native click/shortcut forwarding retain scene coordinates. Side strips without horizontal flow use the root background independently of theme tint.

The bridge records physical dimensions, resource generation, submitted scene generation and hardware/WARP selection. DWM owns source-frame lifetime; these counters are **not** WebKit compositor frame IDs and do not establish atomic delivery of asynchronous layout/DOM observations. An unchanged scene is not rebuilt to refresh animation. Device removal recreates presentation resources without navigation. Construction failure releases resources and restores native styles; hardware setup failure retries the same D3D11 route with WARP. Unsupported composition reports a localized capability error with native detail, without GDI material fallback.

Normal Windows builds compile `DevDuo.Windows.Compositor.dll` with the detected Visual Studio C++ tools/Windows SDK. Each application evidence session freezes its build manifest/native source hashes alongside C# compiler checksums, assets, the runtime manifest and frozen runtime build inputs. mise retains ownership of portable tools. Simulator measurement configuration is unchanged.

The application harness covers 24 Safari states, exact Fit, fixed-bottom frames, viewport units/ranges, language/document/scroll preservation, immersive mode, appearance/backdrop separation, disposal and unavailable-runtime failure. ## Fractional boundary rasterization

The current runtime requires **content painting v2**, while retaining viewport API v2 and content color API v1. `WKViewSetHostUnderPageBackgroundColor(view, rgb)` supplies the same explicit opaque root-background fallback used by the host boundary strips. The setter changes the native under-page color and invalidates only when that color changes; navigation resets it to white until a current-document observation arrives. It does not change page CSS or geometry. The runtime manifest, required export and frozen patch hashes distinguish this runtime from painting v1; rebuild older runtimes.

The approximately 94% Fit seam combined two raster issues. The host enclosed a content clip using damage-style floor/ceil, although Skia's hard clips use nearest-pixel edges. For the observed 594-pixel page edge at backing scale 0.939914, the edge is 558.31 pixels: the painter stops before column 558, but the old host fill began at 559. Boundary and footer clips now use half-up nearest-pixel rounding on all four edges; damage rectangles remain conservative. The standalone diagnostic uses the same clip rule.

Additional fractional cases exposed transparent pixels at the software backing-store edge. `SetDIBitsToDevice` ignores alpha, so transparent premultiplied pixels became opaque black. The native software painter now composites over the explicit under-page background and then white before GDI upload, without stretching content or copying edge pixels. `WM_PRINTCLIENT` now converts physical client damage to logical damage just as `WM_PAINT` does, preventing diagnostic paints from being cropped twice by fractional scale.

`BoundaryChecks.cs` uses an unmodified solid static fixture across eight mappings and six window sizes. Its one-shot `WM_PRINTCLIENT` evidence measures software paint before DWM/chrome; it is neither final GPU output nor a rendering input. The presented harness additionally records authored fixed/sticky frames and viewport units for cross-DPI preservation. Explicit **Capture observation** also saves software-paint evidence; automatic observations remain metadata-only. See [the native acceptance record](009-WINDOWS-HANDOFF.md#native-acceptance-checklist) for actual DPI and presented-window coverage.

## Validation limits

### Safari scroll indicators

The [Device Hub scroll-indicator research](003-CALIBRATION-WORKFLOW.md#safari-scroll-indicators), retrieved from dev `55e1c35`, defines the behavior target. Windows Safari presentation suppresses painting and hit testing for the main document's native vertical scrollbar while retaining its overlay layout. Nested and horizontal scrollbars, immersive presentation, page styles and viewport reservations keep their existing behavior. No injected CSS hides the native scrollbar.

The required **host scroll-indicator API v1** passes the policy through WebPage creation parameters and exposes asynchronous document epoch, root scroll position/range, computed CSS suppression and a native user-motion sequence. A single WebCore-owned weak state store separates document lifetimes. Native wheel/keyboard paths establish intent; programmatic scroll requests clear it, and actual vertical movement is required. Layout range/viewport changes invalidate intent. The host also requires recent native input, rejects stale navigation/geometry callbacks and starts hidden. Zero range, `scrollbar-width: none`, and the native custom scrollbar's hidden/zero-width style suppress the indicator; merely changing DOM scrollY does not show it. This is a bounded native intent/motion association, not a universal causal guarantee for simultaneous page mutation and input.

The passive DirectComposition visual follows the whole scene's outer right edge, including Safari's side reservation, and uses the existing presentation transform and screen mask. It has no host input or accessibility rectangle. A local thumb surface moves independently of the glass tree; fade changes its opacity rather than repainting the page. Current approximations are a black thumb with maximum opacity 0.55, width 3 and outer gap 3 scene units, a track inset 4 from top/bottom, minimum thumb length 24, a 700 ms hold and 300 ms fade. These are engineering parameters, not physical-device measurements or exact Safari timing. macOS system WebKit and other scroller classes are outside this Windows correction.

Run `just test-windows-scroll-indicators` on an unlocked desktop for the scoped Closed portrait checks. They distinguish actual trusted input, native motion telemetry, unchanged DOM geometry, source-raster absence of a second scrollbar and final desktop thumb pixels. Include fresh idle, native wheel/keyboard, endpoint fade, instant/smooth script scrolling, canceled-wheel script scrolling, short `overflow:scroll` documents, CSS `none` and custom `display:none`/`width:0`. A stable post-fade interval also checks that native update, indicator-query and full-scene generation counts stop growing. Other poses, touch deceleration, nested/horizontal scrollers and macOS need separate native acceptance; builds and pure state tests do not establish those results.

### Translucent fixed overlays

Alpha compositing inside the layout viewport and color extension outside it are separate capabilities. A full-screen `position: fixed; inset: 0` mask still ends at the actual layout viewport. Following [WebKit's backdrop implementation](https://github.com/WebKit/WebKit/commit/2ae949b78743), the obscured inset uses a solid color blended against the page background rather than continued striped content. The user-provided Safari observation and its scope are recorded in [Calibration](003-CALIBRATION-WORKFLOW.md#translucent-modal-backgrounds).

The required **fixed-container color API v1** (`WKViewGetFixedContainerColorAPIVersion`, `WKViewRequestFixedContainerColors`) asynchronously queries WebCore's existing `fixedContainerEdges` through ordinary IPC. It returns four edge states and opaque RGB values, including native recognition of dialog backdrops and dimming layers. It neither changes layout nor writes the page's fixed-color history cache. Windows fills only the actual obscured strips, including valid-flow pixels beneath them; successful empty or unsupported results clear old colors. The legacy DOM footer field remains diagnostic and cannot override the native result. The runtime manifest requires `hostFixedContainerColorApiVersion: 1`; rebuild older engines.

The Windows edge-metadata path also multiplies a renderer's background alpha by its own computed `opacity` before native blending. This repairs a solid black mask with `opacity: .5` returning solid black despite half-transparent viewport painting. Opacity one retains the original color path. The change does not alter actual page painting and does not infer ancestor group opacity or arbitrary filters. The macOS system engine has not received this local correction.

The existing 200 ms native timer requests at most one sample in flight when rendering updates change. Navigation and geometry changes invalidate pending results; document, navigation, geometry and request generations reject stale callbacks. A timeout clears the color and allows retry. `webKit.continuation.fixedContainerColorExtension` records status, revision, per-edge colors and provenance. Sampling can lag changing paint; unsupported multi-color edges remain explicit rather than pretending arbitrary visual content is a single color.

`just test-windows-fixed-overlay` uses the independent `fixed-overlay.html` fixture to check viewport alpha and inset solid colors separately, preserving document identity, viewport, scroll, fixed rectangles and viewport units. It covers ordinary masks, native dialog backdrops, expanded/compact reservations and side insets. Source raster, final desktop pixels and original Safari comparisons remain different evidence. Do not enlarge the viewport or add document padding to reproduce the extension. The macOS bridge enables the system implementation when its capability is available; that changed path still requires native macOS acceptance.

### Shell material and dynamic state

Composition API v3 separates drawing kinds from click actions and adds DirectWrite measurement using the drawing font. Address, menu, bookmarks and overview expand the shell; only the reload glyph reloads. The plus remains a return-to-top illustration. `SafariChromeState` correlates native wheel/keyboard intent with same-direction document movement. Downward cumulative travel >24 or upward >8 changes state; intent expires after 350 ms. Viewport clamps and zero/opposite motion retain state; script scroll alone does not compact. Navigation resets expansion and input. This bounded correlation does not establish exact causality for concurrent scripts/native input.

`config/safari-shell.json.windowsMaterial` owns Windows art parameters: blur 14 scene units, saturation 1.8, brightness 1.05, contrast 1.02, top highlight 0.35, edge highlight 0.30, sheen 0.08, shadow blur 10 and downward offset 3. Existing Tint/Glass/Shadow/Radius preferences still apply. Saturation/brightness/contrast use a ColorMatrix, because DirectComposition's saturation effect accepts only 0–1. Rounded tint, directional highlights, rim and shadow approximate the layered recipes from [design.dev](https://design.dev/tools/liquid-glass-generator/) and [Hire Digital](https://hiredigital.com/tools/liquid-glass-css-generator). This is not physical refraction or Apple's private Liquid Glass kernel. Top background, floating surfaces and tab track are separate; surface glyph color follows independent shell appearance while material thickness adapts to backdrop brightness. Unbacked Closed clock/Wi-Fi glyphs follow root-background contrast; document boundaries remain independent.

Passive camera, Wi-Fi and local `HH:mm` illustrations reuse macOS scene coordinates. Closed portrait shows all three in both shell states; Closed landscape shows only the camera at the appropriate side. Open expanded shows clock/Wi-Fi; Open compact and immersive show none. A minute change refreshes the clock even on static pages. Names are localized, and these illustrations never consume page clicks.

The independent **content color API v1** (`WKViewGetContentColorAPIVersion`, `WKViewRequestContentEdgeColor`) uses ordinary snapshot IPC internally and returns only request ID, status and RGB. It samples the bottom unobscured edge in Closed and the top in Open, at most 18 logical rows, rescaled to width 64 without device scale. The native code averages unpremultiplied sRGB channels and ignores alpha <= 0.1. No sampled image enters presentation or crosses the host ABI. Status 0 is success, 1 invalid input, 2 unavailable/no usable pixels and 3 unsupported format. Startup requires `contentColorApiVersion: 1` in the integrity-checked runtime manifest; rebuild older runtimes with the source-build recipe.

### Presented scroll regression

The presented follow-up exposed a further fractional-scroll defect: after a smooth return to scrollY=0, the static page could retain shifted rows and a narrow strip of old pixels. `DrawingAreaWC` is the active Windows drawing area in this pin. Its non-composited updates previously sent logical scroll deltas to Skia backing-store copies that truncate scaled offsets to integer pixels. The Windows-only host patch now uses ordinary scroll-region damage painting when a delta cannot be represented as an integer device-pixel translation, clearing any queued copy first. Integral translations retain the copy path. This runs on native scroll updates, with no repaint timer, forced-repaint loop, page modification or viewport change. Fractional scrolling can therefore paint more pixels than the old copy optimization.

## Inspector, navigation and first paint

`patches/0003-windows-developer-api.patch` adds host developer API v1: selective removal of the dedicated debugging user script, explicit native Inspector TCP start/stop and per-store proxy settings. The integrity manifest and startup now require `hostDeveloperApiVersion: 1`, alongside viewport/painting/content-color/appearance versions. All three patch hashes and current frozen inputs must match; the older two-patch runtime must be rebuilt. This changes developer capabilities, not logical screen or viewport reservations.

The Developer tools group separates local Inspector, native remote inspection and page CDP/chii. Native remote uses WebKit's unauthenticated `webkit-inspector-socket` TCP protocol and excludes a simultaneous local Inspector. It defaults to loopback, opens LAN only when selected and releases the listener on stop/disposal. Page CDP uses the independent token-protected native message bridge and packaged chii frontend; it does not translate WebKit Inspector traffic. Windows proxies support system/direct/custom native network settings. See [developer architecture](001-ARCHITECTURE.md#developer-tools-and-page-proxy) and [acceptance scope](009-WINDOWS-HANDOFF.md#developer-tools-acceptance).

The Developer tools group's local Inspector buttons, **F12** and **Ctrl+Shift+I** control the active page's native Web Inspector. Developer extras are enabled in Release as well as Debug. The host connects the Inspector, detaches it before showing it, and keeps it in a separate window so docking does not reserve device viewport space. Closing the Inspector window updates host state; disposal closes the frontend. Opening local Inspector does not start remote listeners or enable testing IPC. Elements, Console, Network, Storage and Timelines are supplied by the pinned WebKit frontend; the separate chii option supplies Chrome DevTools for the qualified page CDP subset.

Rotation updates the existing WKView's geometry, masks, viewport reservations and live composition/input transform. It does not navigate, replace the document or clear its JavaScript/form/history state. Scroll may clamp when the valid range changes. The app-owned calibration page updates query labels with `history.replaceState`; arbitrary developer pages receive no relabeling. Fold and container-mode changes still recreate the view.

Before the first validated document-extent observation, only unverified inset continuation receives the fallback fill. The layout viewport remains live: covering the entire frame until DOMContentLoaded would hide WebKit's early paints behind a white host surface. The delayed-script regression verifies an exposed real layout viewport while the document is still loading. This does not make external CSS, scripts, DNS or TLS faster.

Saved `webKit.timings` separate one-time runtime verification, native initialization, request-to-navigation-start, navigation commit, finish and first document observation. These are host milestones, not presented-frame timestamps. Use Inspector **Network** and **Timelines**, plus Navigation/Resource Timing, to distinguish connection/response delay from parsing, script execution and painting. Performance runs retain raw details only in ignored captures; they do not establish a general WebKit-versus-Chromium benchmark.

The Windows IPC transport previously opened the source process before importing each cross-process handle. Local HTTP and resource-free inline pages reproduced the same roughly 2.5-second delay, and native profiling isolated it inside `OpenProcess(PROCESS_DUP_HANDLE)` rather than the managed navigation call. A defensive copy of a registered process capability also reproduced a 2.84-second `DuplicateHandle` pause. The underlying cause of those Windows calls' delay was not established. Release compiler optimization alone did not remove it.

The source patch now gives each auxiliary process an inherited parent process capability. Before GPU initialization, the UI uses existing launcher handles to push a GPU process capability into Web and a Web process capability into GPU. The launcher uses an explicit two-handle inheritance allowlist; children validate the pipe's server identity and clear inheritance flags. Each receiver adopts its target-owned handle before checking the connection token or pipe, so rejection also releases it. Separate processed/accepted acknowledgments distinguish rejection from canceled delivery. A pending transfer holds an exact target-process handle and terminates that target if adoption is never acknowledged; it never reclaims a remote numeric handle that the child may have reused. Ordinary IPC payloads retain their transfer/close-source ownership rules. Lookup takes a thread-safe strong reference under a lock without copying the process handle; teardown removes the registration after its last connection owner while in-flight lookups retain the capability. A failed registered operation cannot silently retry `OpenProcess`. Child capabilities are limited to the duplication operation, but this is an IPC optimization, not a new process sandbox boundary. Existing ordinary IPC pipe send-failure limitations are not claimed to be repaired by the capability-transfer guard.

Network-to-Web resource handles use the same capability registry. The UI pushes the Network capability before replying to the synchronous connection request. Request and attempt generations cover both Web-side retries and the data store's internal Network restart; a newer attempt replaces only the pending source for that request. Valid connection information moves the source into the connection before IPC opens. Close and failed attempts clear it promptly. This bootstrap alone carries an explicit safe-dispatch flag, because an internal asynchronous retry runs outside the original synchronous handler while Web is still waiting for its reply. Ordinary message-dispatch policy remains unchanged.

Connection preferences and permissions are sampled after the bootstrap acknowledgment and peer-identity checks, immediately before sending the creation request. Sampling them before the asynchronous bootstrap could retain initial disabled Service Worker preferences while provisional-page setup enabled the Web process. Network preference updates sent before a connection exists are not retained, so the stale snapshot caused generated IPC validation to reject legitimate Service Worker messages and terminate the new page process. The fix preserves that validation and restores the configuration-update ordering.

Windows remote Canvas backends complete the two-phase GPU initialization on the main dispatcher before entering their isolated synchronous stream. That stream intentionally does not pump unrelated parent messages, so entering it before the parent bootstrap acknowledgment would create a wait cycle. A retained GPU/backend reference and stream-identity checks protect reentrant close or replacement; initialization failure invalidates the captured stream on its owning dispatcher instead of entering the long readback wait.

Both GPU handshake phases check actual source registration, initialization and connection validity within one deadline. A named wait may report that a message was already dispatched by the shared sync queue, or may consume an older token; neither result alone proves success or failure. The Windows path rechecks state without extending the deadline. Other platforms retain their original wait behavior.

Unknown-document observations use one verification worker that reads the renderer's existing observation snapshot. Messages arriving during that read mark another read as necessary, including messages for an already accepted document; they cannot race a second writer or be silently dropped behind an older document's verification. Navigation generations and disposal reject stale results. This does not rerun the page observer or its Canvas sampling. A deterministic old/new/old message sequence failed before this change and passes with the drain.

`just test-windows-navigation-latency` runs separate cold HTTP and cold inline processes, then alternates the same resource-free document between inline and HTTP navigation. It checks real completion, the first document observation and page animation progression, rather than only moving a wait before the navigation-start callback. The cold HTTP case also times the first matching source-raster pixels from the original request, using the existing passive `GetDC`/`BitBlt` reader without a paint request. This is an observed upper bound, not a final DWM presentation timestamp. The same recipe launches a separate `--navigation-latency-network-retry` process that terminates its own first Network child and checks bounded document recovery with the same Web process; process replacement alone does not identify which retry layer ran. `just test-windows-browser-identity` checks native request headers and page-visible UA through redirects, subsequent navigation, both containers and rotation. These bounded local-host regressions do not establish external-site speed or final desktop frame rate.

The native test harness's `--browser-tools` mode covers both folds, all eight rotations, JavaScript/form/history identity, delayed-script early painting and the Inspector button. `--browser-performance` is an opt-in network diagnostic for the color laboratory and MDN homepage, with Inspector enabled. `--storage-write` followed by `--storage-read` in separate processes checks localStorage, IndexedDB and persistent cookies; both require the same absolute `DEVDUO_WEBKIT_PROFILE` and a unique `DEVDUO_STORAGE_TEST_TOKEN`. Ordinary native tests use isolated temporary profiles rather than the user's website data. Windows execution does not validate the matching macOS scene-update bridge.

`mise exec -- just package-local-windows` builds a self-contained unsigned preview under `temp/build/local-release/win-x64/DevDuo` and archives it in `temp/local-release/`. It uses and verifies the existing source-built runtime, frozen inputs and notices without requiring a published archive pin. It preserves the original native-acceptance flag and does not claim that current build orchestration rebuilt the engine. Formal release packaging retains its separate published-runtime requirements.
