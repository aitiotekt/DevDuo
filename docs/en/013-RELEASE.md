# Releases and repository administration

## Current scope

DevDuo is an experimental Avalonia workbench, with a macOS WKWebView baseline and Windows WebKit implementation with scoped native viewport/continuation acceptance; broader input, DPI and compatibility acceptance remains pending. Linux platform validation and releases are disabled by `[platforms.linux]` (`check = false`, `release = false`). Workflow planning and documentation may still run on Ubuntu. Build success and signing do not establish native acceptance or rights to redistribute simulator-derived geometry. Preserve the [third-party notices](../../THIRD_PARTY_NOTICES.md).

The release workflow builds self-contained .NET 10 packages for **macOS 27 arm64** and **Windows x64**. Windows exclusively requires the pinned source-built WebKit host runtime, published independently and fetched by exact metadata version into the Windows application archive under `webkit/`. Install its complete `bin` directory and manifest beside the app under `webkit/`, or set an absolute `DEVDUO_WEBKIT_RUNTIME`; missing or incompatible files fail explicitly. The official prebuilt testing runtime cannot substitute for host API v2. See [Windows WebKit setup](014-WINDOWS-WEBKIT.md#avalonia-backend). macOS uses GitHub's `xcode-27` preview runner, verified against the [runner image inventory](https://github.com/actions/runner-images#available-images); runner availability is an external dependency. Existing `just package-macos` remains an unsigned, framework-dependent development bundle. Release packaging preserves the existing `local.DevDuo.Calibration` bundle identity and uses the native app host directly.

## CI responsibilities and resource budget

| Trigger / job | Work | Limit and boundary |
| --- | --- | --- |
| Checks: `main`, PR, manual, reusable | One Ubuntu portable job runs Python/JS, Core/Localization/CDP service tests, lint, typecheck, release consistency and strict docs build | 30 minutes; portable setup never restores an application backend |
| Checks: native matrix | Metadata-enabled macOS and Windows compile the app, native bridge and native test harness; macOS also executes AppKit geometry assertions | 30 minutes each; no interactive browser acceptance, private captures, engine download or WebKit source build |
| Documentation push / manual | Relevant `main`/`release` paths build deployment inputs; only `main` deploys | Build 30 minutes, deploy 15 minutes; PR docs are already covered by Checks |
| Application Release | Reusable Checks must pass before platform packaging/signing | macOS 120, Windows 60, assembly/publication 30 minutes each |
| Manual WebKit release | Incremental full engine build on the persistent self-hosted Windows runner | Build step 22 hours, complete job 23 hours; hosted planning/publication never compiles WebKit |

Only a **complete docs-only PR diff** may skip the native matrix. Unknown comparison ranges require full checks. Every `main` push still compiles native targets: a preceding code push may have been cancelled before it passed. Reusable application release verification always forces native compilation. Checks cancels superseded runs on the same ref; documentation also cancels superseded deployments. All jobs check out the immutable triggering SHA with checkout credential persistence disabled. Read-only PR jobs never use the engine runner, signing environments or publication credentials.

Application and engine releases each have a global serial group with `queue: max` and `cancel-in-progress: false`. GitHub allows up to 100 waiting runs; a full queue rejects further runs. Ordering follows entry into the wait queue, not dispatch order. See [GitHub concurrency semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency). Current actionlint 1.7.12 lacks the new `queue` schema; `.github/actionlint.yaml` suppresses only that exact diagnostic on these two files. Remove those narrow compatibility exceptions when the tool supports the syntax.

Intermediate platform, engine and documentation preview artifacts expire after **one day**; final application artifacts after **seven days**. ZIP uploads disable redundant compression. Main documentation uploads only its Pages artifact. Persistent engine caches and mise tool installs stay on the self-hosted disk. Self-hosted jobs do not read or write the GitHub Actions cache. GitHub-hosted jobs still use that cache. Retention reduces storage time but cannot make a large first runtime upload fit an account's remaining artifact quota: check current usage before dispatch, and remove expired disposable artifacts through repository administration. Release assets remain the durable runtime dependency. Hosted execution, storage and cache have different billing/limits; consult the current [Actions billing rules](https://docs.github.com/en/billing/concepts/product-billing/github-actions) and [runner/resource limits](https://docs.github.com/en/actions/reference/limits), rather than assuming public execution makes all storage unlimited.

## Download trust and installation help

Official macOS application releases require Developer ID signing, Apple notarization and a stapled ticket. Windows application releases currently have no Authenticode signature, so Windows may show an unknown-publisher or reputation prompt. Source/development bundles are unsigned; they are not the official macOS release download. Certificate provisioning and signing mechanics are maintained below, not in the user quick start.

Download application ZIPs only from the project's [GitHub Releases](https://github.com/aitiotekt/DevDuo/releases). If an app is blocked or reported as damaged, first confirm the platform and system version in the [installation table](../../README.md#download-and-install), then extract a fresh copy of the complete application ZIP. Do not mix files from different releases. If the problem remains, report the exact system message and release version in an issue; no certificate installation or system-wide protection change is part of normal installation.

## Windows WebKit runtime releases

Application dev/build/package recipes run `just prepare-debugging` to copy the exact root pnpm-locked chii/chobitsu browser assets and license texts into `temp/build/debugging/`; MSBuild copies that tree into the application output/publish directory as `debugging/`. The installed app serves these offline with .NET and its native WebView; it neither requires a user Node installation nor starts the chii Node server. Retain the generated manifest and license directory in every package. Missing assets fail explicitly when CDP is enabled. Windows runtime packages must additionally provide `hostDeveloperApiVersion: 1` and the third developer patch; a successful older viewport build is insufficient. Native runtime acceptance remains distinct from resource packaging and CDP transport tests.

`[webkit]` in `devduo-metadata.toml` owns the independent engine version, tag/asset prefixes, Windows target, DLL identity, upstream revision, manual-release branch and runner labels. The current ABI keeps the upstream `WebKit2.dll` name; the ZIP name is derived as `<asset_prefix>-<version>-win-x64.zip`. Application version changes do not bump the engine. `runtime.lock.json` remains the official diagnostic archive lock and must agree with the metadata upstream revision; an upstream upgrade also requires reviewing the native bindings and their required capabilities.

`.github/workflows/webkit-release.yml` accepts **only `workflow_dispatch`**, on the metadata branch. Its plan runs on a hosted runner; the engine build runs on the configured self-hosted Windows/x64 labels. The workflow must first exist on the default branch for manual dispatch to be available. The existing infrastructure configuration registers a native Windows service runner directly to this repository with a persistent work directory. Metadata selects its default `["self-hosted", "Windows", "X64"]` labels, without depending on its private machine label or registering another runner. All matching runners available to the repository are eligible; if more are added, use an infrastructure-managed capability label in `runner_labels` to restrict routing. [GitHub documents default label matching](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/use-in-a-workflow#using-default-labels-to-route-jobs).

**aitiotekt-infra** owns the self-hosted Windows runner deployment and short physical work directory, with build tools available to LocalSystem. Windows/Git long-path settings remain required; `CMAKE_OBJECT_PATH_MAX` does not extend compiler capabilities. Workspace migration retains the previous checkout and caches.

Checkout uses `clean: false` and does not gate on the state of the persistent workspace. Do not run `just clean` on this build workspace between jobs. Ninja output stays in `temp/build/windows-webkit-host/`; downloads, source pins, vcpkg binary packages and recorded patch sets stay in `temp/cache/windows-webkit/`. Build trees are archived/restored under `temp/build/windows-webkit-trees/` when the upstream revision, compiler hash, Windows SDK/VC tool versions change. A legacy tree without that identity is preserved separately and requires a fresh build once. Exact recorded patch sets can be refreshed without discarding unrelated source edits; unexpected changes fail explicitly. Archived trees consume disk until deliberately removed; no automatic cleanup claims to preserve them indefinitely. The build step is limited to 22 hours and the complete job to 23 hours, below the [24-hour `GITHUB_TOKEN` lifetime](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idtimeout-minutes). If a cold build times out, rerun it against the same persistent workspace to continue Ninja work; do not clean it first.

Release sequence:

1. Set a new `[webkit].version` and keep the intended source revision/patches. Review and merge these inputs onto the configured branch.
2. Manually run **WebKit runtime release** with `dry-run=true` to prepare artifacts without publishing, then `dry-run=false` to publish. An existing version ZIP and its sidecars are reused directly; engine tool installation and native compilation are skipped. Otherwise the runtime is built and packaged with exports, notices and source records. The hosted publisher creates the tag at the package's source commit when it is missing, creates a draft when no release exists, uploads only missing assets and publishes with `latest=false`. Existing assets are never replaced or compared.
3. Windows application packaging downloads the exact version asset, unpacks it and bundles it under `DevDuo/webkit/`. A cached download for the same version is reused. There is no `latest` lookup or automatic engine build.

Use `mise exec -- just test-webkit-release-tools` for tooling tests. `package-webkit-release` reuses or creates the version package; `publish-webkit-release` publishes it. `just release-preflight` only requires a published release containing the version asset. The pipeline does not compare archive, file, source or build hashes; `SHA256SUMS`, the runtime manifest and build provenance remain outputs for downloaders. ZIP extraction accepts legacy Windows backslash paths; new packages use standard `/` paths.

## Version and trigger rules

[`devduo-metadata.toml`](../../devduo-metadata.toml) owns the version, application identity, URLs and release policy. `just set-version VERSION` synchronizes it with both Node manifests and the native project. `just bump-version LEVEL` supports `major`, `minor`, `patch`, `alpha`, `beta`, `prerelease` and `stable`; prerelease counters start at zero. For example, `0.1.0-dev` → `alpha` yields `0.1.0-alpha.0`, then `prerelease` yields `0.1.0-alpha.1`.

After editing the TOML version directly, run `just sync-version`. `just check-version` and `just release-check` detect version drift. Changing versions does not publish or create a tag. Update both changelogs separately.

| Source | Version | Result |
| --- | --- | --- |
| `release` branch | `X.Y.Z-dev` | Explicit successful skip; no package or publication |
| `release` branch | `X.Y.Z-alpha.N` / `X.Y.Z-beta.N` | Verify, build, sign, attest and publish a prerelease |
| Exact `vX.Y.Z[-alpha.N/-beta.N]` tag | Matching package version | Verify and release; stable versions require approval |
| Other branch or mismatched tag | Any | Reject before accessing signing credentials |

Pushes to `release` and `v*` tags trigger **automatic publication**, as before. Manual dispatch defaults to `dry-run=true`: verification, signed/notarized packages, assembly, attestations and Actions artifacts still run, while tag creation and Release publication are skipped. Set `dry-run=false` explicitly for a manual publication. This option does not suppress publication triggered by a separate push. Manual dispatch uses the selected ref and its `github.sha`; all jobs check out that triggering commit. Before platform builds, planning requires the metadata WebKit version to be published with its asset. The macOS signing job checks all six environment inputs and its SDK before building; presence checks do not certify the validity of the certificate or Apple credentials. Reusable Checks derives its platform matrix from metadata and reruns portable tests, localization tests, lint/typecheck, a docs build and native macOS/Windows compilation before signing jobs can start. Release jobs are serialized. Credentials are never passed to PR or reusable verification jobs.

Stable versions require the `stable-release` environment approval. Both prerelease and stable macOS packages require Developer ID signing and Apple notarization; unlike the reference project's configurable unsigned prereleases, this workflow has no unsigned release fallback. Signing uses a secure timestamp, hardened runtime and the .NET JIT entitlement. Release resources and managed assemblies live in `Contents/Resources`; relative links preserve .NET assembly/resource lookup and local native-runtime probing from both directories. Native Mach-O libraries are signed first; the outer bundle signs its main executable last. `just test-macos-bundle`, also run in macOS CI, tests resource aliases and native ad-hoc signature verification after ZIP extraction without Apple credentials. The app is then notarized, stapled and checked with Gatekeeper before archiving. See [Microsoft's macOS deployment guidance](https://learn.microsoft.com/en-us/dotnet/core/deploying/macos).

Alpha and beta both skip stable approval. Packaging, assembly and publication use explicit cancellation and direct-dependency success conditions, so the skipped approval does not suppress later jobs. Failed or cancelled builds still stop assembly/publication; dry-run mode completes assembly and skips only publication.

## Artifacts and retries

An existing application tag is reused as is; publication does not compare it with the triggering commit. Reuse the original `release-final` artifact for publication recovery instead of replacing signed bytes.

- `DevDuo-vVERSION-osx-arm64.zip`: signed/notarized `.app`, bundled .NET and notices.
- `DevDuo-vVERSION-win-x64.zip`: portable self-contained directory and notices; **no Authenticode signature**.
- `release-manifest.json`: exact version, source ref/SHA, expected files, sizes, SHA-256 hashes, platform signing facts and the bundled Windows WebKit version/tag/asset/upstream revision.
- `SHA256SUMS`: hashes for both archives and the manifest. All four downloadable files receive GitHub build provenance attestations. These do not make Windows display a verified publisher.

These hashes and attestations are outputs for downloaders; no pipeline step verifies them. Assembly copies both platform archives and writes the manifest and checksums. Publication creates the tag when missing, creates a draft when no release exists, uploads only assets the release does not have and then publishes a draft. Existing assets are never replaced or compared, and an already published release only receives missing assets. If an interrupted upload leaves an unfinished asset, inspect the draft before retrying; the tooling will not delete it automatically. Rebuilding signed binaries can change bytes, so retry publication with the original `release-final` artifact. WebKit releases always use `latest=false`. Release hashing uses bounded buffers instead of reading a whole engine archive into memory.

Release staging uses ignored `temp/build/release/`; final archives and reports use `temp/release/`. Separate `packages.net10.0.osx-arm64.lock.json` and `packages.net10.0-windows.win-x64.lock.json` keep release runtime dependencies locked without changing ordinary development restores. To deliberately regenerate them, use `dotnet restore` with `-p:RuntimeIdentifier=osx-arm64` or `-p:RuntimeIdentifier=win-x64 -p:DevDuoWindows=true -p:EnableWindowsTargeting=true`, plus `--force-evaluate`; review dependency changes.

## GitHub administration and documentation

The separate **aitiotekt-infra** repository owns the DevDuo entry in `meta/github-repositories.yml`: read-only default workflow permissions, a protected `release` branch, approval/signing/Pages environments and Pages configuration. Maintain/Admin direct pushes may bypass the merge check, but cannot bypass release workflow verification; a separate safety rule forbids force pushes and deletion. The former aggregate `Checks report` job was removed; required PR status checks must name the remaining Checks jobs. Do not manually duplicate these settings in application scripts.

The `release-signing` environment accepts only `release` and `v*` tags and needs `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_PASSWORD` and `APPLE_TEAM_ID`. Infrastructure references the shared Developer ID certificate through SOPS and OpenBao; no credentials belong in this repository. Stable approval allows the sole maintainer to self-review and forbids administrator bypass.

Documentation is configured for **https://dev-duo.aitiotekt.com/**, with VitePress base `/`. Documentation installs the locked Python audit tools, rejects private/publication-input violations before packaging the Pages artifact, and builds on `main`, `release` and PRs; only `main` deploys through the `github-pages` environment. Infrastructure owns the DNS-only CNAME to `aitiotekt.github.io` and Pages custom domain. Apply those settings and provision environment secrets before running releases. Enable Pages HTTPS enforcement after GitHub has issued its certificate.
