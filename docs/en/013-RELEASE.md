# Releases and repository administration

## Current scope

DevDuo is an experimental Avalonia workbench, with a macOS WKWebView baseline and Windows WebKit implementation with scoped native viewport/continuation acceptance; broader input, DPI and compatibility acceptance remains pending. Linux platform validation and releases are disabled by `[platforms.linux]` (`check = false`, `release = false`). Workflow planning, reports and documentation may still run on Ubuntu. Build success and signing do not establish native acceptance or rights to redistribute simulator-derived geometry. Preserve the [third-party notices](../../THIRD_PARTY_NOTICES.md).

The release workflow builds self-contained .NET 10 packages for **macOS 27 arm64** and **Windows x64**. Windows exclusively requires the pinned source-built WebKit host runtime, published independently and fetched by exact metadata version/hash into the Windows application archive under `webkit/`. Install its complete `bin` directory and manifest beside the app under `webkit/`, or set an absolute `DEVDUO_WEBKIT_RUNTIME`; missing or incompatible files fail explicitly. The official prebuilt testing runtime cannot substitute for host API v2. See [Windows WebKit setup](014-WINDOWS-WEBKIT.md#avalonia-backend). macOS uses GitHub's `xcode-27` preview runner, verified against the [runner image inventory](https://github.com/actions/runner-images#available-images); runner availability is an external dependency. Existing `just package-macos` remains an unsigned, framework-dependent development bundle. Release packaging preserves the existing `local.DevDuo.Calibration` bundle identity and uses the native app host directly.

## CI responsibilities and resource budget

| Trigger / job | Work | Limit and boundary |
| --- | --- | --- |
| Checks: `main`, PR, manual, reusable | One Ubuntu portable job runs Python/JS, Core/Localization/CDP service tests, lint, typecheck, release consistency and strict docs build | 30 minutes; portable setup never restores an application backend |
| Checks: native matrix | Metadata-enabled macOS and Windows compile the app, native bridge and native test harness; macOS also executes AppKit geometry assertions | 30 minutes each; no interactive browser acceptance, private captures, engine download or WebKit source build |
| Documentation push / manual | Relevant `main`/`release` paths build deployment inputs; only `main` deploys | Build 30 minutes, deploy 15 minutes; PR docs are already covered by Checks |
| Application Release | Reusable Checks must pass before platform packaging/signing | macOS 120, Windows 60, assembly/publication 30 minutes each |
| Manual WebKit release | Incremental full engine build on the persistent self-hosted Windows runner | Build step 22 hours, complete job 23 hours; hosted planning/publication never compiles WebKit |

Only a **complete docs-only PR diff** may skip the native matrix. Unknown comparison ranges require full checks. Every `main` push still compiles native targets: a preceding code push may have been cancelled before it passed. Reusable application release verification always forces native compilation. Checks cancels superseded runs on the same ref; documentation also cancels superseded deployments. All jobs check out the immutable triggering SHA with checkout credential persistence disabled. Read-only PR jobs never use the engine runner, signing environments or publication credentials.

Application and engine releases each have a global serial group with `queue: max` and `cancel-in-progress: false`. GitHub allows up to 100 waiting runs; a full queue rejects further runs. Ordering follows entry into the wait queue, not dispatch order. See [GitHub concurrency semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency). Current actionlint 1.7.12 lacks the new `queue` schema; `.github/actionlint.yaml` suppresses only that exact diagnostic on these two files, while YAML tests validate the complete concurrency mappings. Remove those narrow compatibility exceptions when the tool supports the syntax.

Intermediate platform, engine and documentation preview artifacts expire after **one day**; final application artifacts after **seven days**. ZIP uploads disable redundant compression. Main documentation uploads only its Pages artifact. Persistent engine caches and mise tool installs stay on the self-hosted disk. Self-hosted jobs do not read or write the GitHub Actions cache. GitHub-hosted jobs still use that cache. Retention reduces storage time but cannot make a large first runtime upload fit an account's remaining artifact quota: check current usage before dispatch, and remove expired disposable artifacts through repository administration. Release assets remain the durable runtime dependency. Hosted execution, storage and cache have different billing/limits; consult the current [Actions billing rules](https://docs.github.com/en/billing/concepts/product-billing/github-actions) and [runner/resource limits](https://docs.github.com/en/actions/reference/limits), rather than assuming public execution makes all storage unlimited.

## Windows WebKit runtime releases

Application dev/build/package recipes run `just prepare-debugging` to copy the exact root pnpm-locked chii/chobitsu browser assets and license texts into `temp/build/debugging/`; MSBuild copies that tree into the application output/publish directory as `debugging/`. The installed app serves these offline with .NET and its native WebView; it neither requires a user Node installation nor starts the chii Node server. Retain the generated manifest and license directory in every package. Missing assets fail explicitly when CDP is enabled. Windows runtime packages must additionally provide `hostDeveloperApiVersion: 1` and the third developer patch; a successful older viewport build is insufficient. Native runtime acceptance remains distinct from resource packaging and CDP transport tests.

`[webkit]` in `devduo-metadata.toml` owns the independent engine version, tag/asset prefixes, Windows target, DLL identity, upstream revision, manual-release branch, runner labels and consumed archive SHA-256. The current ABI keeps the upstream `WebKit2.dll` name; the ZIP name is derived as `<asset_prefix>-<version>-win-x64.zip`. Application version changes do not bump the engine. `runtime.lock.json` remains the official diagnostic archive lock and must agree with the metadata upstream revision; an upstream upgrade also requires reviewing the native bindings and their required capabilities.

`.github/workflows/webkit-release.yml` accepts **only `workflow_dispatch`**, on the metadata branch. Its plan runs on a hosted runner; the engine build runs on the configured self-hosted Windows/x64 labels. The workflow must first exist on the default branch for manual dispatch to be available. The existing infrastructure configuration registers a native Windows service runner directly to this repository with a persistent work directory. Metadata selects its default `["self-hosted", "Windows", "X64"]` labels, without depending on its private machine label or registering another runner. All matching runners available to the repository are eligible; if more are added, use an infrastructure-managed capability label in `runner_labels` to restrict routing. [GitHub documents default label matching](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/use-in-a-workflow#using-default-labels-to-route-jobs).

Use a persistent checkout at a stable absolute path. Before checkout, a Windows job runs `git config --global` for both `core.symlinks` and `core.longpaths`; that writes only the job account's configuration. The runner work directory plus the engine tree exceeds `MAX_PATH`, so the host must also have Windows long paths enabled before the compiler can create those paths. The runner account needs real symlink privileges, Git for Windows/Bash, Windows PowerShell, mise and the Visual Studio C++/Clang + Windows SDK system components. The configured service uses LocalSystem: prerequisites must be visible to that service account, rather than only an interactive user's profile. mise manages the portable engine tools and GitHub CLI. No private server name belongs in the public configuration. Ordinary PRs and application releases do not dispatch the engine workflow or execute on that runner.

Checkout uses `clean: false` and rejects modified tracked inputs before checkout can reset them, then checks the resulting workspace again. Do not run `just clean` on this build workspace between jobs. Ninja output stays in `temp/build/windows-webkit-host/`; downloads, source pins, vcpkg binary packages and recorded patch sets stay in `temp/cache/windows-webkit/`. Build trees are archived/restored under `temp/build/windows-webkit-trees/` when the upstream revision, compiler hash or Windows SDK/VC tool versions change. A legacy tree without that identity is preserved separately and requires a fresh build once. Exact recorded patch sets can be refreshed without discarding unrelated source edits; unexpected changes fail explicitly. Archived trees consume disk until deliberately removed; no automatic cleanup claims to preserve them indefinitely. The build step is limited to 22 hours and the complete job to 23 hours, below the [24-hour `GITHUB_TOKEN` lifetime](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idtimeout-minutes). If a cold build times out, rerun it against the same persistent workspace to continue Ninja work; do not clean it first.

A cache directory alone does not establish a successful source checkout. An interrupted initial fetch/checkout with an unborn `HEAD` and no indexed files resumes using its existing Git objects. Partial working files, including unknown edits, are moved intact beside it as `<cache-name>.incomplete-<timestamp>-<id>` before an ordinary checkout; retain those files until reviewed. Nested source and vcpkg repositories set their own Git long-path and symlink options. Existing commits with a different revision/origin, indexed files in an incomplete cache, Git locks and non-repository directories fail explicitly; resolve or preserve those states manually rather than resetting or deleting them.

The build job runs `test-webkit-release-tools` on Windows before installing engine tools and compiling. SSH recovery on 2026-10-24 established the pinned source `HEAD`, preserved all 7,525 partial files with matching SHA-256 hashes and retained both existing object packs. Repeated maintained-patch synchronization and pinned vcpkg initialization passed, as did the Windows packaging/build-tree and source-recovery regressions. These checks do not establish a completed CMake configuration, full engine build or published runtime.

Release sequence:

1. Set a new `[webkit].version`, keep the intended source revision/patches, and clear `archive_sha256` for an unpublished version. Review and merge these inputs onto the configured branch.
2. Manually run **WebKit runtime release** with its default `dry-run=true` to rehearse the build and retain candidate artifacts without creating a tag or Release. Run the same commit again with `dry-run=false` to publish. A candidate hash is not a published pin. It builds the complete runtime, checks required exports, retains upstream notices and source inputs, and uploads a same-run Actions artifact. A hosted publish job verifies its identity/hashes, creates a draft Release, downloads and compares the uploaded bytes, then publishes with `latest=false`. Existing mismatched tags/assets are never overwritten. The self-hosted build job has read-only repository permissions; publication credentials are confined to the hosted job.
3. Copy the actual `archive_sha256` from the release report/job summary into metadata, review that pin and merge it. This separate pin does not change the engine source fingerprint. Until it is set, application release planning and runtime fetching fail explicitly; no checksum or successful first publication is fabricated.
4. Ordinary Windows application packaging fetches exactly that Release tag/asset, verifies the pinned archive digest, validates revision, patch/source fingerprint, API capabilities and every runtime file, then bundles it under `DevDuo/webkit/`. A matching local download cache is reusable. There is no `latest` lookup, automatic engine build, expiring-artifact fallback or official-testing-runtime substitution.

Use `mise exec -- just check-webkit-release` and `test-webkit-release-tools` for policy/integrity checks; the latter includes real ZIP and synthetic persistent-cache checks on Windows. `package-webkit-release` packages a matching native build; `fetch-windows-webkit-runtime` downloads and verifies the metadata pin. `publish-webkit-release` is the workflow's publication command. `just release-preflight` combines configuration validation with a read-only GitHub check of the pinned engine release: it must be published, have the exact asset set, and match the source tag, patch fingerprint, archive pin and checksum report. It intentionally fails while the initial archive pin is empty. The Windows consumer then verifies the actual downloaded archive and every extracted runtime file. Failed downloads/extractions never become reusable complete caches. Release assets are the durable dependency; Actions artifacts are only transport between jobs. See [GitHub self-hosted runner behavior](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners) and [workflow artifact retention](https://docs.github.com/en/actions/tutorials/store-and-share-data).

The workflow does not run interactive desktop acceptance from a runner service. The runtime manifest retains its explicit native-acceptance status; exports, compilation and hashes do not certify rendering, input or DPI. The initial hosted job and subsequent SSH diagnosis confirm runner availability and source-cache preparation; a complete service-account build, GitHub upload/download and an application release using the published pin remain unverified. Retained notices/source provenance do not by themselves complete the redistribution review described in [third-party notices](THIRD_PARTY_NOTICES.md).

## Version and trigger rules

[`devduo-metadata.toml`](../../devduo-metadata.toml) owns the version, application identity, URLs and release policy. `just set-version VERSION` synchronizes it with both Node manifests and the native project. `just bump-version LEVEL` supports `major`, `minor`, `patch`, `alpha`, `beta`, `prerelease` and `stable`; prerelease counters start at zero. For example, `0.1.0-dev` → `alpha` yields `0.1.0-alpha.0`, then `prerelease` yields `0.1.0-alpha.1`.

After editing the TOML version directly, run `just sync-version`. `just check-version` detects version drift; `just release-check` also checks workflow branch/tag filters against metadata. Changing versions does not publish or create a tag. Update both changelogs separately.

| Source | Version | Result |
| --- | --- | --- |
| `release` branch | `X.Y.Z-dev` | Explicit successful skip; no package or publication |
| `release` branch | `X.Y.Z-alpha.N` / `X.Y.Z-beta.N` | Verify, build, sign, attest and publish a prerelease |
| Exact `vX.Y.Z[-alpha.N/-beta.N]` tag | Matching package version | Verify and release; stable versions require approval |
| Other branch or mismatched tag | Any | Reject before accessing signing credentials |

Pushes to `release` and `v*` tags trigger **automatic publication**, as before. Manual dispatch defaults to `dry-run=true`: verification, signed/notarized packages, assembly, attestations and Actions artifacts still run, while tag creation and Release publication are skipped. Set `dry-run=false` explicitly for a manual publication. This option does not suppress publication triggered by a separate push. Manual dispatch uses the selected ref and its immutable `github.sha`; it cannot nominate an unrelated source SHA. All jobs check out that same triggering commit. Before platform builds, planning checks the real published WebKit report and metadata pin. The macOS signing job checks all six environment inputs and its SDK before building; presence checks do not certify the validity of the certificate or Apple credentials. Reusable Checks derives its platform matrix from metadata and reruns portable tests, localization tests, lint/typecheck, a docs build and native macOS/Windows compilation before signing jobs can start. Release jobs are serialized. Credentials are never passed to PR or reusable verification jobs.

Stable versions require the `stable-release` environment approval. Both prerelease and stable macOS packages require Developer ID signing and Apple notarization; unlike the reference project's configurable unsigned prereleases, this workflow has no unsigned release fallback. Signing uses a secure timestamp, hardened runtime and the .NET JIT entitlement. Every bundled Mach-O is signed before the app, then the app is notarized, stapled and checked with Gatekeeper before archiving. See [Microsoft's macOS deployment guidance](https://learn.microsoft.com/en-us/dotnet/core/deploying/macos).

## Artifacts and retries

Planning queries the exact application tag before runtime preflight, compilation or signing. If that version is already tagged at another commit, planning fails explicitly: bump the version or retry the original source/artifact. A documentation-only push to `release` does not bypass version identity or silently succeed. A same-source retry still runs all integrity gates; reuse the original `release-final` artifact for publication recovery instead of replacing signed bytes.

- `DevDuo-vVERSION-osx-arm64.zip`: signed/notarized `.app`, bundled .NET and notices.
- `DevDuo-vVERSION-win-x64.zip`: portable self-contained directory and notices; **no Authenticode signature**.
- `release-manifest.json`: exact version, source ref/SHA, expected files, sizes, SHA-256 hashes, platform signing facts and the bundled Windows WebKit version/tag/asset/archive hash/upstream revision.
- `SHA256SUMS`: hashes for both archives and the manifest. All four downloadable files receive GitHub build provenance attestations. These do not make Windows display a verified publisher.

Assembly requires exactly both platform reports and archives. Publication verifies the downloaded artifact set again, creates or verifies the tag, uploads a draft, downloads and verifies its bytes, then exposes the release. Existing published releases are accepted only when every asset matches. Draft recovery first downloads and compares every existing asset, then uploads only missing files from the identical original artifact set and verifies the complete downloaded set before publication. Changed bytes, channels, source tags, unexpected assets and incomplete already-published releases fail without overwriting anything. If an interrupted upload leaves an unfinished asset, inspect the draft before retrying; the tooling will not delete it automatically. Use the original `release-final` artifact when retrying publication. Rebuilding signed binaries can change bytes; a retry must not silently replace an already published version. No latest-release promotion occurs on a matching no-op retry; WebKit releases always use `latest=false`. Both workflows have an `always()` report job that fails when a required stage fails or is unexpectedly skipped. Release hashing uses bounded buffers instead of reading a whole engine archive into memory.

Release staging uses ignored `temp/build/release/`; final archives and reports use `temp/release/`. Separate `packages.net10.0.osx-arm64.lock.json` and `packages.net10.0-windows.win-x64.lock.json` keep release runtime dependencies locked without changing ordinary development restores. To deliberately regenerate them, use `dotnet restore` with `-p:RuntimeIdentifier=osx-arm64` or `-p:RuntimeIdentifier=win-x64 -p:DevDuoWindows=true -p:EnableWindowsTargeting=true`, plus `--force-evaluate`; review dependency changes.

## First publication checklist

The application and engine candidates are both **0.1.0-beta.1**; their release gates and future version updates remain independent. The first [hosted WebKit attempt](https://github.com/aitiotekt/DevDuo/actions/runs/40045146774) reached the build step on 2026-10-24 but failed on an incomplete source cache without `HEAD`; the overall run was cancelled. That confirms workflow availability, not a complete engine build. `[webkit].archive_sha256` remains empty. Application planning correctly refuses even a dry run until a real engine is published and pinned. Apply the reviewed source-cache recovery fix on the configured release branch before retrying.

The three named environments exist. The current GitHub credential cannot list environment signing secrets or repository runners (HTTP 403); their readiness is **unverified**, not evidence that they are absent. The failed hosted build establishes that a Windows runner accepted the job. No workflow, tag, upload or publication was triggered by the local preparation or subsequent SSH diagnosis. The [macOS integration record](015-PLATFORM-PARITY.md#beta-integration-record-2026-10-24) distinguishes native observations and remaining platform gaps; passing builds alone does not close them.

1. Make the workflow files and complete native source/patch inputs available on the default branch. This local preparation does not commit or push them. Confirm that the repository-scoped Windows runner is online and that its service account sees Git/Bash, mise, the required Visual Studio C++/Clang components, Windows SDK and symlink privileges. Confirm free disk capacity for source, dependencies and archived build trees.
2. Verify the infrastructure-managed `release-signing`, `stable-release` and `github-pages` environments. Check signing secret names without printing their values. Runner/SDK availability and secret contents require actual remote validation.
3. Run `mise exec -- just release-check` and the release-tool tests. Rehearse the manual WebKit build, then explicitly publish it. Read the successful hosted publication summary and pin that archive SHA-256 in metadata; never pin a dry-run candidate alone.
4. Run `mise exec -- just release-preflight` with authenticated GitHub CLI access. Keep engine source/patch/tool pins unchanged between engine publication and application consumption, or publish a new engine version. Preserve both changelogs and review the bundled notices and redistribution status.
5. Finish those prerequisites **before pushing the numbered version to `release`**, because that push publishes automatically. Stable versions instead require their exact version tag and environment approval. A manual rehearsal is available on an already eligible ref; it does not turn off automatic push publication.
6. Check the successful final reports, both platform ZIPs, `release-manifest.json`, `SHA256SUMS` and attestations. On clean target machines, verify extraction, launch and the pinned engine's initialization separately from CI compilation/signing. Windows still requires the Microsoft Visual C++ x64 runtime used by the native toolchain; .NET self-contained packaging does not supply all native C++ prerequisites. See [Microsoft's deployment guidance](https://learn.microsoft.com/en-us/cpp/windows/deployment-in-visual-cpp). Native scene/input/DPI acceptance remains a separate gate.

No workflow is dispatched or release published by these local checks. The first actual hosted runs, Apple signing/notarization, clean-machine startup and public asset round-trip remain external acceptance until executed.

## GitHub administration and documentation

The separate **aitiotekt-infra** repository owns the DevDuo entry in `meta/github-repositories.yml`: read-only default workflow permissions, a protected `release` branch, approval/signing/Pages environments and Pages configuration. Maintain/Admin direct pushes may bypass the merge check, but cannot bypass release workflow verification; a separate safety rule forbids force pushes and deletion. PR merges require the `Checks report` status. Do not manually duplicate these settings in application scripts.

The `release-signing` environment accepts only `release` and `v*` tags and needs `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_PASSWORD` and `APPLE_TEAM_ID`. Infrastructure references the shared Developer ID certificate through SOPS and OpenBao; no credentials belong in this repository. Stable approval allows the sole maintainer to self-review and forbids administrator bypass.

Documentation is configured for **https://dev-duo.aitiotekt.com/**, with VitePress base `/`. Documentation installs the locked Python audit tools, rejects private/publication-input violations before packaging the Pages artifact, and builds on `main`, `release` and PRs; only `main` deploys through the `github-pages` environment. Infrastructure owns the DNS-only CNAME to `aitiotekt.github.io` and Pages custom domain. Apply those settings and provision environment secrets before running releases. Enable Pages HTTPS enforcement after GitHub has issued its certificate. Configuration in source does not itself prove that a deployment, certificate or release exists.
