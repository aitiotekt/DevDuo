# Windows 交接

Windows 唯一使用固定的 WebKit Windows Port，通过 Avalonia 承载。保留 macOS 系统 WKWebView，以及 Safari 外壳和沉浸式两种容器。[WebKit 指南](014-WINDOWS-WEBKIT.md)统一管理源码、复现及详细限制；宿主控件按[路线图](100-ROADMAP.md)推进。

## 导航启动与移动端身份（2026-10-24）

独立冷启动 HTTP 和无外部资源的内联页面都复现了约 2.5 秒的请求至导航开始延迟。原生计时将其中 2497–2547ms 定位在 `OpenProcess(PROCESS_DUP_HANDLE)` 内，托管导航调用约一毫秒。后续防御性进程句柄复制也复现了 2844ms 的 `DuplicateHandle` 暂停。这确定了真实 WebKit 进程中的阻塞操作，但未确定其底层 OS 原因：独立 Win32 探针没有复现同样延迟。仅使用 Release 优化未能解决。

Windows 补丁现继承受限的父进程能力，并由 UI 使用已有启动器句柄，向子进程推送由连接持有的 Web/GPU/Network 能力。查找通过线程安全引用保活，不复制进程句柄。实际 UI 向子进程推送约为 0.002–0.003ms，同轮诊断中的接收端获取仍然很慢。原生检查覆盖继承隔离、共享所有权、并发移除、有效载荷传递、无效句柄及未确认传递的清理。[WebKit 指南](014-WINDOWS-WEBKIT.md#inspector导航与首帧)说明生命周期和重试规则。

调查还发现了进程切换后首次 Canvas 的独立 15 秒等待环：隔离流开始等待时，主调度器尚未处理父连接上的 GPU 引导。补丁在进入该流前完成 GPU 初始化，并防护重入导致的流替换。早先失败批次和原始计时分别保留；导航开始、文档完成、观测交付、源像素和最终桌面呈现属于不同里程碑。

进一步反复导航暴露了异步 Network 引导中的配置顺序缺陷。诊断批次记录了等待前捕获的版本 0／Service Worker 关闭、确认时当前版本 1／开启，以及 Network 端点收到的旧版本 0。生成的 Service Worker IPC 校验随后在进入处理函数前拒绝合法消息，UI 因此结束临时 Web 进程。现改为确认及对端检查后、临发送时构造连接参数，保留校验并使用当前配置。独立的旧/新/旧观测消息回归还证明并修复了托管验证期间丢失新文档首次报告的窗口；并未把每次历史超时都推断为该原因。

## 文档末端延伸调研（2026-10-22）

官方 Windows WebKit `324423@main` 探针提供了应用源码运行时的对照基线。其报告的 `scrollY=1820`、视口高 580、文档高 2400 时旧行号残留，不是 Safari 应有的目标效果。本机 iOS 27.1 Device Hub Safari 在受控的 2400 CSS 像素条纹页中没有重复行号：Y=1770 时，视口下方继续显示剩余 50 像素普通流，之后填页面底色；Y=1820 时，整个 98 像素 inset 都使用背景。符合条件的紫色通栏 fixed 底栏会向该区域延伸颜色；移除底栏后再显示窄标记时使用根背景。颜色延伸的判定和历史与旧文档像素残留不同。本次使用夹具 `scrollTo`，没有独立重跑 Windows 滚轮测试。原始窗口 PNG、DOM 记录和夹具源码保存在本地 `captures/desktop-validation/document-end/`。

对于顶部 inset 为零、未缩放的场景，设 `D` 为根文档高度、`Y` 为实际 scrollY、`V` 为未遮挡视口高度、`B` 为底部 inset，有效延伸长度为 `L = clamp(D - Y - V, 0, B)`。保留 `[V, V+L)` 中的实时内容，每次相关更新都在最终原生绘制表面明确清除并补色 `[V+L, V+B)`。本例从 `2400 - 580 - 98 = 1722` 之后开始出现补色区域。保留 `D`、`V`、滚动范围和 fixed 框；添加 DOM padding 或过早盖住整个 inset 都会改变语义或隐藏有效内容。CSS 坐标必须按真实 zoom/DPI 转换。只刷父 HWND 背景无法清除不透明子窗口或后备表面中保留的旧像素。

补色优先使用引擎解析出的页面底层/canvas 背景，html/body 背景回退须明确标注；不要复制最后一行，也不要直接拿工具栏主题着色当页面背景。fixed 底栏颜色延伸作为独立的外观能力处理。[WebCore 的 `insetClipLayerRect`](https://github.com/WebKit/WebKit/blob/6a67801395e5dfc1a7ac4ceb60ddd2ca9735aa2d/Source/WebCore/page/LocalFrameView.cpp#L2763) 在文档边界裁剪延伸；[Cocoa 的 fixed 颜色延伸视图](https://github.com/WebKit/WebKit/blob/6a67801395e5dfc1a7ac4ceb60ddd2ca9735aa2d/Source/WebKit/UIProcess/API/Cocoa/WKWebView.mm#L3692) 属于额外的原生行为，[underPageBackgroundColor](https://developer.apple.com/documentation/webkit/wkwebview/underpagebackgroundcolor) 定义页面边界外的底色。应检查 Windows Port 的裁剪、失效区域和后备表面清理；这些是排查方向，尚非确认的根因。修改原生集成时补验滚轮/程序滚动、短文档、文档高度变化、两种底部 inset，以及离开末端后再返回。

首次 macOS 对照发现了独立的灰色 canvas/底栏未延伸问题，没有重复行号。现已恢复 WebKit canvas 绘制，并增加纯色通栏 fixed 底栏的被动颜色近似层。98/80 两种底部 inset 和底栏移除均已检查，真实视口、fixed 框及滚动范围未改变；见[回归流程及边界](003-CALIBRATION-WORKFLOW.md#文档末端与原生位置回归)。此 macOS 修复不代表实验性 Windows 后备表面问题已经解决或验收。

触控/鼠标输入在已解锁桌面运行 `mise exec -- just test-windows-interaction`，覆盖文档起始仿真、轻点/滑动、原生滚轮拦截/恢复，不重建文档的 REST/UI 模式切换，以及网页与 Safari 栏上的圆形指针和离开手机后的普通指针恢复。既有滚轮驱动验收明确选择鼠标模式。fixed-overlay 矩阵同时检查交角的侧边优先。这些新增原生场景需要在 Windows 执行，交叉编译不等于像素/输入通过。
